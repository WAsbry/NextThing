# NextThing 页面地图与用户流程

> 更新时间：2026-06-12  
> 当前阶段：梳理页面与用户流程，不修改 Compose UI。

## 1. 盘点口径

- 以 `NextThingNavigation.kt` 中的真实路由为准。
- 页面是占据完整屏幕、能够独立进入和返回的用户界面。
- 弹窗、Bottom Sheet、菜单和加载/空状态不单独算页面，但在所属页面下检查。
- 当前共确认 **26 个路由级界面**：5 个主导航页面、21 个流程页或辅助页。

## 4. 用户操作流程

### 流程 1：首次进入

`启动页 → 权限与初始化 → 登录页 → 今日页`

回访用户：

`启动页 → 今日页`

### 流程 2：核心任务闭环

`今日页/底部创建 → 创建任务页 → 输入或语音 → AI 解析 → 用户确认 → 创建成功 → 今日页 → 任务详情 → 完成任务`

这是第一优先级，也是第一批 HTML 原型的主流程。

### 流程 3：任务创建高级配置

`创建任务页 → 分类管理/分类编辑 → 返回创建页`

`创建任务页 → 自定义重复 → 返回创建页`

`创建任务页 → 通知策略 → 返回创建页`

`创建任务页 → 添加地理围栏 → 新建地点 → 地图选点 → 返回并保存`

### 流程 4：日常执行

`今日页 → 任务详情 → 开始专注 → 暂停/继续 → 完成专注 → 返回今日页`

异常处理：

`今日页 → 延期 → 延期原因 → 今日页`

`今日页 → 取消 → 取消原因 → 今日页`

### 流程 5：查找与回顾

`任务页 → 搜索/筛选/切换视图 → 任务详情`

`今日页 → 日历页 → 选择日期 → 任务详情`

`统计页 → 指标/图表 → 趋势详情或任务明细`

### 流程 6：个人与设置

`我的 → 用户信息/成就/主题/视图偏好/同步`

`我的 → 地理围栏设置 → 地点详情 → 关联任务`

## 6. 第一批 HTML 原型范围

第一批不追求覆盖全部功能，而是先确定应用的整体视觉语言和核心操作节奏。

一个 HTML 文件内展示以下手机画面：

1. 启动页
2. 登录页
3. 今日页正常状态
4. 今日页空状态
5. 创建任务初始状态
6. 创建任务录音状态
7. AI 解析状态
8. 单任务确认状态
9. 任务详情状态
10. 完成任务反馈

第一批需要共同确认：

- NextThing 的整体气质和主色，而不是先固定 Design Token。
- 今日页的信息优先级。
- 创建入口是否足够突出。
- AI 能力应该显眼到什么程度。
- 创建任务的状态切换是否自然。
- 任务详情的主操作是完成、编辑还是开始专注。
- 完成任务后的反馈强度。

## 7. 当前结论与待确认项

已确认：

- 先讨论页面与流程，再做 HTML，再实现 Compose。
- 以核心任务闭环作为 UI 重构主线。
- 设置和地理围栏不进入第一批 HTML。
- 技术重构、公共组件和设计规范属于 UI 定稿后的实现产物。

进入 HTML 前需要通过第一批原型共同确认：

- 产品定位更偏“克制的任务工具”还是“主动的 AI 任务伙伴”。
- 今日页是否保留天气、进度概览、多个任务分区。
- 底部创建入口采用普通导航项还是突出的中心操作。
- 登录页在当前个人项目阶段是否需要重点设计。

## 8. 第一批原型

- 原型文件：`html效果图/00_核心流程_V1.html`
- 覆盖范围：启动、登录、今日、今日空状态、创建、录音、AI 解析、确认、详情、完成反馈。
- 视觉方向：克制的 AI 任务伙伴。
- 设计假设：突出 NextThing 和核心操作，天气、统计、高级配置降为辅助信息。

本轮评审顺序：

1. 整体气质与紫色方向是否适合 NextThing。
2. 今日页是否应该只突出一个 NextThing。
3. 底部中央创建按钮是否需要明显高于其他导航项。
4. 创建页默认隐藏高级配置是否合理。
5. AI 解析过程是否需要展示处理步骤。
6. 任务详情是否采用“默认查看、点击编辑”。
7. 完成反馈是否过强或过弱。

验证状态：

- 已完成 HTML 结构与页面跳转目标检查。
- 浏览器视觉检查因本机浏览器运行权限问题待补。

### 今日页 V1 评审

用户反馈：

- 顶部问候语没有必要。
- NextThing 能突出重点，但卡片元素过多，应当只是摘要。
- 查看详情应通过点击卡片进入，并在详情页展示分类、重要程度等信息。
- “开始专注”的点击结果和产品含义不清楚，不适合直接放在首页。
- “接下来”只展示最近几条任务是正确方向。
- 天气比较重要，可以比 V1 更完整。
- 当前进度条价值偏弱，呈现方式也过于弱化。

V2 调整：

- 删除问候语。
- 顶部改为日期、任务数量和增强天气摘要。
- NextThing 卡片删除分类、重要程度和双按钮，只保留标题与时间摘要。
- 整张 NextThing 卡片点击进入任务详情。
- 暂时移除“开始专注”，待专注功能流程单独讨论。
- 删除首页进度条，完成数量并入日期摘要。

### 今日页状态更新交互

第一版尝试在 NextThing 左侧增加完成方框，但该方案破坏摘要卡的完整性，且没有沿用项目已有交互，因此撤回。

最终方案基于现有 `TodayScreen.TaskItem`：

- 点击 NextThing 卡片：进入任务详情页。
- 向左滑动卡片：露出“完成 / 延期 / 放弃”三个操作。
- 向右滑动或再次点击卡片：收起操作区。

首页点击完成后的反馈：

1. 当前任务淡出。
2. 下一条最近任务提升为新的 NextThing。
3. 底部显示“已完成”Snackbar，并提供撤销。
4. 不进入完整庆祝页，避免打断连续操作。

延期和放弃沿用现有原因选择流程。卡片表面保持纯摘要，不增加永久可见的状态按钮。

### 今日页 V3 信息架构

根据讨论，撤销“独立 NextThing 大卡”方案，调整为：

1. 顶部综合摘要卡：日期、天气、今日待办、逾期、今日完成。
2. 首页任务区域只展示待办，不展示已完成任务列表。
3. 下一件待办放在列表第一项。
4. 第一项与其他任务使用同一种任务卡结构。
5. 通过左侧主题色竖条和 `NextThing` 小标签突出第一项。
6. 点击任务进入详情，左滑显示完成、延期、放弃。
7. 完成第一项后，它从首页消失，下一条自动提升为 `NextThing`，摘要数字同步变化。

设计目的：

- 摘要负责说明“今天整体是什么情况”。
- 列表负责处理“具体有哪些待办”。
- NextThing 只是待办列表中的动态身份，不再成为独立组件。
- 首页保持干净，只服务尚未完成的事情。

### 今日页 V4 摘要视觉

V3 将待办、逾期、完成设计为三个等权数字，视觉上接近统计仪表盘，与首页任务导向不符。

V4 调整为：

- 日期和天气仍位于摘要卡上半部分。
- 下半部分改为一句状态叙事：“今天还有 3 件待办”。
- “1 件已逾期”作为次级风险提示，不与待办等权。
- “已完成 2”缩小为右侧绿色反馈胶囊。
- 去除三列布局和竖向分割线。

信息权重：

`待办数量 > 逾期提醒 > 已完成反馈`

摘要负责帮助用户理解今天的状态，不承担统计分析。

### 今日页 V5 竞品研究结论

参考 Things 3、Todoist、Structured 和 Apple 提醒事项后，撤销 V4 摘要方案。

共同规律：

- Things 的 Today 直接组织日历事件和待办，详细字段在需要时再展开。
- Todoist 的 Today/Upcoming 重点是任务分组、完成入口和快速创建。
- Structured 只因为采用时间轴模型，才把时间结构作为页面主视觉。
- Apple 提醒事项的统计数字卡位于列表总入口，不位于具体的 Today 列表。

NextThing 今日页 V5：

- 移除待办、逾期、完成数字摘要。
- 这些数据后续放到“任务”页的信息总览或筛选入口。
- 顶部仅保留“今天”、具体日期和轻量天气。
- 主体直接进入纯待办列表。
- 已完成任务仍不在首页展示。
- NextThing 继续作为列表第一项的动态标签，而不是独立摘要组件。

### 日期、节日、位置与天气规则

#### 日期区域

常规日期：

`6月13日`

`周六 · 农历四月廿八`

节日或节气当天：

- 主标题保持公历月日，不再重复底部导航的“今日”。
- 第三行独立显示节日或节气，如“端午”“中秋”“夏至”。
- 节气优先于普通节日，沿用 `ChineseDateHelper.secondaryText` 的现有规则。
- 不同时展示多个节日名称，避免顶部变成日历百科。

示例：

```text
6月19日
周五 · 农历五月初五
端午 · 粽香安康
```

普通日期不保留第三行空位，顶部高度随内容自然变化。

节日文案规则：

- 格式：`节日名 · 专属短语`。
- 短语优先 4 个汉字，整体建议不超过 9 个汉字。
- 必须包含节日独有意象，不能使用“宜陪伴家人”这类通用句。
- 使用本地固定映射，不在首页临时调用 AI 生成，保证长度和表达稳定。
- 没有合适短语时只显示节日名，不强行补文案。

示例：

| 节日/节气 | 第三行 |
|---|---|
| 春节 | 春节 · 新岁纳福 |
| 元宵 | 元宵 · 灯火团圆 |
| 清明 | 清明 · 春雨寄思 |
| 端午 | 端午 · 粽香安康 |
| 七夕 | 七夕 · 星河相会 |
| 中秋 | 中秋 · 月满人间 |

普通商业节日应克制使用，避免让任务首页变成节日营销入口。

节日第三行视觉规则：

- 保留在日期块第三行，但使用内容自适应的轻量节日签，不占满整行。
- 节日名使用稍强的暖色与字重。
- 祝福短语使用更弱的中性色，不与日期主标题竞争。
- 不使用前置圆点、emoji 或高饱和大色块。
- 节日签属于日期信息的一部分，不设计成可点击按钮。

数据来源：

- 公历日期和星期：系统 `LocalDate`。
- 农历、节气、节日：现有 `ChineseDateHelper`。

#### 定位区域

紧凑标题只显示：

1. `district`，如“浦东新区”。
2. district 为空时显示 `city`。
3. city 为空时显示 `locationName`。
4. 定位不可用时显示“位置不可用”，不能伪造默认城市。

不在首页直接显示街道、完整地址、经纬度和定位精度。点击位置后再展示：

- 城市、区县、街道或完整地址。
- 定位精度与更新时间。
- 刷新位置入口。

数据来源：高德定位 SDK。当前模型定义了 `city / district / province / address / accuracy`。

实现注意：

- 高德转换当前会把“区县 + 街道”拼入 `locationName`。
- `location.address` 尚未写入 `LocationInfo.address`，当前完整地址可能为空。
- 实现位置详情前需要补齐 address 映射，首页紧凑展示不受影响。

#### 天气区域

天气在 NextThing 中的定位不是装饰或完整天气预报，而是**计划执行条件**。

首页紧凑展示：

- 天气图标。
- 当前温度。
- 天气状态。
- 区县位置。
- 当前最影响任务执行的一个风险指标。

风险指标优先级：

1. 气象预警，如暴雨、高温、大风。
2. 未来任务时段的降水概率。
3. 高紫外线等级。
4. 强风、极端高温或低温。
5. 无明显风险时只显示位置，不强塞湿度等指标。

示例：

- `浦东新区 · 2小时后有雨`
- `浦东新区 · 降水 70%`
- `浦东新区 · 紫外线强`
- `浦东新区`

#### 点击天气

点击整个天气与位置区域，打开“天气与今日计划”Bottom Sheet：

- 当前天气、区县和更新时间。
- 未来几个关键时段的天气与降水概率。
- 紫外线或气象预警。
- 与今日任务发生冲突时展示“计划影响”卡片。
- 可直接进入任务时间调整，也可以忽略本次提醒。

不进入独立的完整天气应用，也不在首页堆叠七日预报。

#### 创建与执行干预

天气干预必须满足：

- 任务具有明确日期和时间。
- 任务可能受天气影响，例如户外、出行、运动、拍摄或带有地点。
- 天气风险达到阈值。

创建任务时：

- AI 解析完成后增加非阻断提示，如“19:00 降水概率 70%，是否提前？”
- 用户可以接受建议、保持原计划或不再提醒此任务。
- 不自动修改任务时间。

任务执行前：

- 天气发生显著变化时，通过应用内提示或任务通知补充提醒。
- 示例：“跑步时段可能下雨，建议提前或改为室内运动。”
- 同一任务、同一风险避免重复提醒。

点击天气后的建议必须展示“任务时间 + 天气证据 + 建议”，不能只显示泛化的“注意天气”。

#### 所需和风天气数据

- 实时天气：当前已接入。
- 逐小时天气：提供任务时段降水概率，用于短期任务干预。
- 每日预报：提供最高/最低温和紫外线指数。
- 分钟级降水：适合未来两小时临近降雨提醒。
- 天气指数：可提供紫外线、防晒、穿衣等生活指数。
- 气象预警：用于高优先级风险提示。

当前暂不显示：

- 最高/最低温：代码中只是当前温度 ±3 的临时估算。
- 空气质量：PM2.5 当前为默认值。
- UV 指数：当前为默认值。
- 基于默认 PM2.5/UV 生成的生活建议。

原型中的紫外线与降水概率属于目标设计，需接入对应和风天气接口后才能进入 Compose 实现。当前实现通过 JWT 请求实时天气 API，不具备这些真实字段。

#### 异常状态

- 定位加载：`正在定位…`
- 无定位权限：`开启定位`，点击进入权限流程。
- 定位失败但有缓存：显示缓存区县，并标记数据更新时间。
- 天气加载：保留位置，只显示轻量加载状态。
- 天气失败：显示位置，不显示温度；点击可重试。
- 日期与节日完全使用本地计算，不依赖网络。
