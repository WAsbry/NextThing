# NextThing 项目优化总体方案

> 目标：将本项目的 Android 端技术深度做到极致，作为跳槽互联网大厂的核心简历亮点项目。
> 原则：每一项优化都要有**量化数据**和**面试话术**，面试官要的是"你解决了什么问题"，不是"你做了什么功能"。

---

## 一、四大优化方向总览

| 优先级 | 方向 | 预计耗时 | 面试价值 |
|:---:|---|:---:|---|
| P0 | 性能优化 | 2-3 周 | 必问，有数据最直观 |
| P0 | 架构演进（模块化 + MVI 规范化） | 2-3 周 | 展示架构思维，3 年经验必须具备 |
| P1 | 数据同步方案（离线优先架构） | 1-2 周 | 差异化亮点，大部分候选人讲不出来 |
| P1 | 稳定性 & 工程质量 | 1-2 周 | 展示工程素养，加分项 |

## 二、P0 - 性能优化

### 2.1 冷启动优化

**现状分析：**
- `NextThingApplication.kt` 在 `onCreate` 中做了大量初始化：Timber、WorkManager 初始化、注册 8 个周期性 Worker、注册地理围栏
- `MainActivity.kt` 启动后加载首页（TodayScreen），涉及数据库查询 + 天气网络请求 + 定位
- 这些全部在主线程串行执行，拖慢首屏渲染

**优化手段：**

| 手段 | 具体做法 | 预期收益 |
|---|---|---|
| 启动链路打点 | 在 Application.onCreate 首尾、Activity.onCreate、首屏 Composable 首次渲染处打点，用 `SystemClock.uptimeMillis()` 或 `ComponentsUsageLogger` 量化 | 建立基线数据 |
| 延迟初始化 | 将非首屏必需的初始化（地理围栏注册、成就检查 Worker、倒计时 Worker）延迟到首屏渲染完成后执行，使用 `CoroutineScope(Dispatchers.IO).launch` | 减少 30-50ms |
| App Startup | 用 Jetpack App Startup 替代 Application 中的手动初始化，实现懒加载 | 解耦初始化逻辑 |
| WorkManager 按需注册 | 检查 8 个 Worker 是否全部需要启动时注册，部分可改为 `PeriodicWorkRequest` + `ExistingPeriodicWorkPolicy.KEEP` 避免重复注册 | 减少 Worker 注册开销 |
| 首屏数据预加载 | 在 Application 中提前触发 Room 数据库预热（简单查询），避免首屏查询时冷 IO | 首屏加载提速 |

**量化目标：** 冷启动时间降低 30% 以上（需先建立基线）。

**面试话术：**
> "我对应用做了全链路冷启动分析，通过打点发现 Application.onCreate 占了总耗时的 60%。我将非首屏必需的初始化（地理围栏、定时任务）延迟到首屏渲染后执行，并使用 App Startup 管理初始化顺序，最终将冷启动时间从 X ms 降到 Y ms。"

### 2.2 Compose 性能优化

**现状分析：**
- 项目有 17 个 Screen，15 个共享组件，全部使用 Compose
- TodayScreen 最为复杂：任务列表 + 天气卡片 + 定位信息 + 统计摘要
- 可能存在的性能问题：不必要的重组（recomposition）、LazyColumn item 不稳定、StateFlow 粒度过粗

**优化手段：**

| 手段 | 具体做法 | 预期收益 |
|---|---|---|
| 重组分析 | 开启 `compose.compilerReports`，使用 Layout Inspector 或 `RecompositionCounter` 定位高重组频率的 Composable | 精准定位瓶颈 |
| @Stable / @Immutable | 为 domain model（Task, Category, WeatherInfo 等）添加 `@Immutable` 注解，确保 Compose 跳过不需要的重组 | 减少无效重组 |
| derivedStateOf | 在 LazyColumn 的滚动监听、搜索过滤等场景中使用 `derivedStateOf`，避免每次状态变化都触发重组 | 减少重组次数 |
| remember / key | 在 LazyColumn 中使用 `key(task.id)` 确保列表增量更新；对计算密集的 UI 逻辑使用 `remember` 缓存 | 列表性能提升 |
| StateFlow 粒度拆分 | ViewModel 中避免一个 `StateFlow<UiState>` 包裹所有状态，按功能拆分为多个 `StateFlow`，减少下游重组范围 | 精准重组 |

**量化目标：** 首屏帧率稳定 60fps，TodayScreen 重组次数降低 50%。

**面试话术：**
> "我通过 Compose Compiler Report 发现 TodayScreen 每次任务列表刷新时会触发 40+ 次无效重组。原因是 UiState 粒度过粗，一个字段变化导致整个页面重组。我通过拆分 StateFlow 粒度 + @Immutable 注解 + derivedStateOf，将重组次数降到个位数，帧率从 45fps 稳定到 60fps。"

### 2.3 内存优化

**现状分析：**
- 地理围栏 BroadcastReceiver 长期持有 Context
- ASR 语音识别使用 WebSocket 长连接
- 天气服务定时请求，图片加载（Coil）
- WorkManager Worker 可能持有过期引用

**优化手段：**

| 手段 | 具体做法 |
|---|---|
| LeakCanary 集成 | 重新启用 LeakCanary，跑一遍完整功能流程收集泄漏点 |
| WeakReference / LifecycleAware | 对 GeofenceReceiver、ASR WebSocket 等长生命周期对象使用生命周期感知的引用管理 |
| Bitmap / Image 管理 | 检查 Coil 图片加载配置，确保设置合适的缓存大小和内存策略 |
| 对象池 / 缓存策略 | 天气数据使用 5 分钟缓存（已有），检查是否有不合理的内存缓存膨胀 |
| Profiler 分析 | 用 Android Studio Memory Profiler 做一次完整操作后的内存快照对比 |

**面试话术：**
> "我通过 LeakCanary + Memory Profiler 发现了 3 处内存泄漏：地理围栏 BroadcastReceiver 持有 Activity Context、ASR WebSocket 未在生命周期销毁时断开、WorkManager Worker 持有过期 ViewModel 引用。通过改用 Application Context、Lifecycle 感知释放、WeakReference 等方式修复。"

---

### 2.4 包体积优化

**现状分析：**
- 已启用 R8 minify + 资源压缩
- 依赖了高德地图 SDK（map2d + location + search）、BouncyCastle、Retrofit 等
- Release APK 当前体积未知

**优化手段：**

| 手段 | 具体做法 |
|---|---|
| APK Analyzer 分析 | 用 Android Studio APK Analyzer 查看各部分占比，找出体积大户 |
| 资源优化 | 压缩 / 转换 res 下的图片资源为 WebP，移除无用资源 |
| 语言资源过滤 | `android.defaultConfig.resConfigs("zh", "en")` 只保留中英文资源 |
| SO 库过滤 | `ndk.abiFilters` 只保留 `armeabi-v7a` 和 `arm64-v8a` |
| 动态特性 | 考虑将导出功能（XLSX/CSV）作为可选依赖 |

## 三、P0 - 架构演进

### 3.1 模块化拆分

**现状：** 单模块架构，所有代码在 `app` 模块下，按包名分层（data / domain / presentation）。

**目标：** 组件化多模块架构，按功能拆分独立 module。

**拆分方案：**

```
:app                          # 壳模块（Application、Navigation、DI聚合）
:feature:today                # 首页
:feature:tasks                # 任务列表
:feature:create               # 任务创建/编辑
:feature:taskdetail           # 任务详情
:feature:stats                # 统计
:feature:focus                # 番茄钟
:feature:settings             # 设置
:feature:achievement          # 成就系统
:feature:geofence             # 地理围栏
:core:data                    # 数据层（Room、Retrofit、Repository实现）
:core:domain                  # 领域层（Model、Repository接口、UseCase）
:core:common                  # 工具类、扩展函数
:core:designsystem            # 主题、通用UI组件
:core:service                 # 天气、定位、AI、语音等服务实现
```

**分步推进：**
1. 先抽 `core:domain` 和 `core:common`（纯 Kotlin，无 Android 依赖，风险最低）
2. 再抽 `core:data`（Room + Retrofit，需要处理好 DI）
3. 再抽 `core:designsystem`（Compose 主题和组件）
4. 最后按功能拆 `feature:*`（涉及 ViewModel 和 Screen 联动）
5. `:app` 只保留 Application、Navigation、DI Module 聚合

**面试话术：**
> "项目初期是单模块 Clean Architecture，随着功能增长到 17 个页面、100+ 源文件，编译时间明显变长，模块边界也开始模糊。我将项目演进为组件化架构，通过 api implementation 分层实现编译隔离，壳模块只负责 Navigation 和 DI 聚合。增量编译时间从 X s 降到 Y s。"

### 3.2 MVI 规范化

**现状：** 使用了 StateFlow，但部分 ViewModel 的状态管理不够规范（副作用用LiveData混用、事件处理不统一）。

**目标：** 所有页面统一 MVI 模式。

**规范定义：**

```
Intent（用户意图）
    ↓ sealed class / sealed interface
Reducer（状态归约）
    ↓ 纯函数，oldState + intent → newState
State（UI 状态）
    ↓ @Immutable data class
SideEffect（一次性事件）
    ↓ SharedFlow / Channel（导航、Toast、Snacknar）
```

**改造要点：**
- 每个 Screen 定义自己的 `Contract`，包含 `State`、`Intent`、`Effect`
- ViewModel 中 `StateFlow<State>` 通过 `reduce` 函数统一处理，不散落多处赋值
- 所有用户操作封装为 `Intent`，不再直接调用 ViewModel 方法
- 一次性事件（导航、Toast）用 `SharedFlow<Effect>` 发射，消费后不再重放

**面试话术：**
> "我把所有页面的状态管理统一为 MVI 模式。每个页面定义 Contract（State + Intent + Effect），ViewModel 通过 Reducer 纯函数处理状态变更，保证了状态变化的可追踪和可测试。对比之前的散落式 StateFlow 赋值，MVI 让复杂页面（如任务创建，涉及 10+ 个表单字段）的状态管理变得清晰。"

## 四、P1 - 数据同步方案（离线优先架构）

**现状：**
- 已有 SyncApi、SyncRepository、SyncWorker 骨架代码
- 数据全部存储在 Room 本地数据库
- 后端 API 未部署（baseUrl 为占位地址）

**目标：** 完成一套完整的离线优先同步架构设计并落地，即使没有真实后端也可以跑通本地模拟。

### 4.1 同步架构设计

```
本地 Room（Single Source of Truth）
    ↕ Repository 层同步网关
远程 API（增/改/删 操作同步）
    ↕ WorkManager（约束：网络可用时触发）
```

### 4.2 落地步骤

| 步骤 | 内容 |
|---|---|
| 1. 脏数据标记 | 为所有 Entity 增加 `syncStatus` 字段（SYNCED / PENDING_CREATE / PENDING_UPDATE / PENDING_DELETE） |
| 2. 增量同步查询 | DAO 中增加 `getPendingSyncItems()` 查询，只拉取待同步记录 |
| 3. 冲突解决策略 | 实现 Last-Write-Wins（基于 `updatedAt` 时间戳），处理服务端返回的冲突响应 |
| 4. 同步 Worker | 完善 `SyncTasksWorker`，支持批量上传 + 批量下载 + 错误重试 + 指数退避 |
| 5. 模拟后端 | 用 MockWebServer 或本地拦截器模拟 API 响应，跑通完整同步流程 |
| 6. 同步状态 UI | 在设置页展示上次同步时间、同步状态（同步中 / 成功 / 失败）、手动触发同步按钮 |

**面试话术：**
> "我设计了一套基于 Room + WorkManager 的离线优先同步方案。本地数据库作为 Single Source of Truth，所有写操作先写本地并标记为 PENDING，由 WorkManager 在网络可用时批量同步到服务端。同步冲突采用 Last-Write-Wins 策略，基于 updatedAt 时间戳判定。整个方案通过 MockWebServer 跑通了完整流程。"

## 五、P1 - 稳定性 & 工程质量

### 5.1 崩溃治理

| 手段 | 具体做法 |
|---|---|
| 全局异常捕获 | 自定义 `UncaughtExceptionHandler`，记录崩溃日志到本地文件 |
| 崩溃分类 | 按 Module 归类（数据库崩溃、网络崩溃、UI 崩溃），统计崩溃率 |
| ANR 防护 | 使用 `StrictMode` 检测主线程 IO，确保所有数据库/网络操作在 IO 调度器 |
| 关键路径保护 | 任务保存、定时通知触发等核心路径加 try-catch + 降级策略 |

### 5.2 自动化测试

| 测试类型 | 覆盖范围 |
|---|---|
| 单元测试 | 核心业务逻辑：TaskUseCases（14 个操作）、GeofenceUseCases、AchievementChecker、RepeatFrequency 解析 |
| Repository 测试 | 使用 `androidx.room:room-testing`，对 DAO 做集成测试（内存数据库） |
| ViewModel 测试 | 验证 Intent → State 的映射关系，使用 Turbine 测试 Flow |
| Compose UI 测试 | 关键页面（任务创建、TodayScreen）的端到端测试 |

### 5.3 CI/CD

| 配置 | 内容 |
|---|---|
| GitHub Actions | 配置 lint + test + debug build 自动化流水线 |
| Lint 规则 | 自定义 lint 规则检测常见问题（主线程 IO、硬编码字符串等） |
| Detekt | Kotlin 代码静态分析，统一代码风格 |

## 七、面试表达框架

每一项优化都要按三层来准备：

| 层级 | 面试官会问 | 你要回答 |
|---|---|---|
| **What** | 你是怎么做的 | 具体方案和技术手段 |
| **Why** | 为什么选这个方案 | 和其他方案的对比、取舍 |
| **Deep** | 遇到什么问题 | 踩坑经历、源码级理解、量化数据 |

**示例：**

> **What：** "我对首页做了全链路冷启动优化，通过打点定位到 Application.onCreate 占了 60% 耗时，将非首屏必需的初始化延迟执行。"
>
> **Why：** "对比了 App Startup 和手动的 CoroutineScope 延迟初始化，App Startup 能更好的管理依赖顺序和懒加载，但需要额外的 ContentProvider。考虑到我的初始化有明确的依赖关系，最终选了 App Startup。"
>
> **Deep：** "优化过程中遇到一个问题：延迟初始化地理围栏后，用户如果立刻打开地理围栏页面，围栏还没注册完成。我通过在 ViewModel 中增加初始化状态监听，配合 `stateIn` 让页面等待初始化完成后再加载数据，解决了竞态问题。"
