# NextThing 项目经验（面试导向）

> 以面试考察维度组织，每个点可以独立展开讲 2-3 分钟。

---

## 一、技术栈与架构

**项目定位**：个人任务管理 App，对标滴答清单/Todoist，支持任务 CRUD、分类管理、地理围栏提醒、专注计时、成就系统、天气联动主题。

**技术栈**：Kotlin + Jetpack Compose + Material 3 + Hilt + Room + KSP + Coroutines/Flow + WorkManager + Retrofit + 高德定位SDK + QWeather API

**架构**：单 Activity + Compose Navigation + MVVM（ViewModel + StateFlow）+ Clean Architecture 分层（presentation / domain / data）

**面试话术**：这个项目是我的个人作品，用来练习和展示现代 Android 技术栈。架构上采用了 Clean Architecture 三层分离，presentation 层用 Compose + ViewModel + StateFlow 做单向数据流，domain 层是纯 Kotlin 的 UseCase 和 Repository 接口，data 层用 Room + Retrofit 实现。依赖注入用的 Hilt，从 kapt 迁移到了 KSP。

## 二、定位系统设计（多层 Fallback）

**问题**：国内 Android 设备 Google Play Services 不可靠，需要高德 SDK 做主力定位。

**设计方案**：
```
高德 SDK（省电模式：WiFi+基站，1-2s 出结果）
  ↓ 失败
Google FusedLocationProvider（粗略网络 → 高精度 → lastKnownLocation）
  ↓ 失败
返回 null，UI 展示"获取位置失败"
```

**关键决策**：
- 定位模式选省电（Battery_Saving）而非高精度（Hight_Accuracy），因为室内场景不需要 GPS，省电模式 WiFi+基站 1-2 秒出结果
- 每一层有独立超时（高德 8s、Google 20s、ViewModel 总控 35s），避免无限等待
- 权限检查用 OR 逻辑（COARSE || FINE），兼容 Android 12+ 分级授权

**踩过的坑**：
1. 高德 Key 认证三要素（SHA1 + 包名 + API Key）必须完全匹配，少一个都会返回错误码 7
2. Google FusedLocationProvider 在国内国行 ROM 上基本不可用，不能作为主力定位方案
3. 超时设计要考虑级联累加，外层超时不能打断内层正常流程

**面试话术**：定位系统我设计了三层 fallback——高德做主力（国内体验好），Google FusedLocation 做降级（海外兼容），lastKnownLocation 做兜底。踩了一个 Android 12 权限分级的坑，COARSE 和 FINE 是独立授权的，用 AND 检查会导致只授权粗略位置的用户完全无法定位。

## 三、JWT 认证生命周期管理

**设计**：TokenManager（DataStore）管理 access_token 和 refresh_token，AuthInterceptor 自动注入，登录/注册时保存，登出时清除。

**完整流程**：
1. **登录/注册**：Retrofit 调用后端 → 后端返回 access_token + refresh_token + user 信息 → TokenManager 保存 Token → 创建本地用户 → 同步服务器头像
2. **请求鉴权**：AuthInterceptor 从 TokenManager 读取 access_token → 注入 `Authorization: Bearer` header
3. **Token 刷新**：access_token 过期 → 用 refresh_token 调刷新接口 → 更新 TokenManager
4. **登出**：TokenManager.clear() → 清本地用户数据 → 清导航栈 `popUpTo(0) { inclusive = true }`

**踩过的坑**：
1. 登出时如果不清 Token，AuthInterceptor 会带着旧 Token 自动重新鉴权，等于没登出
2. 登出后不清导航栈，用户可以按返回键回到已登录页面
3. 服务端业务错误（HTTP 400）和真正的网络错误要分开处理，否则用户看到的是"网络错误"而不是"用户名已存在"

**面试话术**：认证系统我用了 JWT + Refresh Token 双 Token 方案，通过 OkHttp Interceptor 自动注入。登出这个功能看起来简单但容易做不完整——必须三步走：清 Token、清本地数据、清导航栈，少一步都会出问题。

## 四、kapt → KSP 迁移

**背景**：项目最初用 kapt 处理注解（Hilt、Room），迁移到 KSP 以提升编译速度。

**遇到的问题**：
1. Hilt 2.48.1 + KSP 不为 BroadcastReceiver 生成 `Hilt_` 基类（ASM transform 失败）
2. 部分 Hilt 绑定缺少 `@Inject constructor` 或 `@ApplicationContext` 限定符，kapt 时代能容忍但 KSP 更严格
3. 阿里云镜像对 KSP 插件返回 502

**解决方案**：
- BroadcastReceiver 用 `@EntryPoint` + `EntryPointAccessors.fromApplication()` 替代 `@AndroidEntryPoint`
- 补全所有缺失的 Hilt 注解
- Gradle 仓库顺序：官方源优先，镜像放后面

**面试话术**：我们把项目从 kapt 迁移到了 KSP，主要为了编译速度。迁移过程中遇到了 Hilt 对 BroadcastReceiver 的兼容性问题——KSP 模式下不会自动生成基类，我用了 Hilt 的 @EntryPoint 模式手动获取依赖来绕过。

## 五、Compose UI 实践

**分类图标渲染**：抽象出 `CategoryIconView` 统一处理三种图标来源（drawable 预置、相册 URI、emoji），所有页面共用一个组件，避免渲染逻辑不一致。

**主题系统**：支持 4 种模式（跟随系统/浅色/深色/跟随天气），天气模式预置 9 套配色，每种天气可自定义主色，通过 DataStore 持久化。

**重复任务**：模板+实例设计——数据库存一条模板（`isTemplate=true`）和每日生成的实例（`isTemplate=false`），编辑实例时同步回模板，避免次日回退。

## 六、Room 数据库设计要点

**迁移策略**：使用自动迁移（AutoMigration）处理字段增减，复杂变更手写 Migration。

**数据流**：Room DAO 返回 `Flow<List<T>>`，通过 `flatMapLatest` + `refreshTrigger` 实现强制刷新，解决 Room InvalidationTracker 偶尔丢失事件的问题。

**重复任务生成**：WorkManager 每日定时触发 `GenerateRecurringTasksWorker`，从模板生成当日实例，通过 `instanceDate` 去重防止重复生成。

## 七、通知系统设计

**功能**：通知策略管理（震动/声音/通知方式/音量）、预置策略、地理围栏联动、声音试听。

**UI 设计决策**：
1. **紧凑布局**：震动 4 选项、声音 3 选项、通知方式 3 选项用 chip 横排（`CompactSelectionSection`），替代列表式竖向排列。选项少于 5 个时横排节省 60%+ 空间，用户一屏看完不需滚动。参考了滴答清单/Todoist/Google Tasks 的设置页设计。
2. **并排展示**：创建任务页通知策略和地理围栏从各占一整行改为并排 `Row(weight(1f))`，两卡片等高 80dp。
3. **弹窗自适应**：策略选择弹窗从固定 60% 屏幕高度改为 `wrapContentHeight` + `heightIn(max=500.dp)`，策略少时不浪费空间。

**预置策略**：`ensurePresetStrategies()` 查 count=0 时插入三条预置（无声提醒/标准提醒/重要提醒），ID 用 `preset_` 前缀区分用户自建数据，`OnConflictStrategy.IGNORE` 防重复。首次使用即有可用策略，降低使用门槛。

**声音试听边界处理**：
1. **勿扰模式崩溃**：原代码调用 `AudioManager.setStreamVolume()` 修改系统音量，DND 模式下抛 `SecurityException: Not allowed to change Do Not Disturb state`。试听不应改系统音量，直接删除该调用。
2. **静音模式无反馈**：`ringtone.play()` 在静音/震动模式下不发声但无提示。播放前检查 `audioManager.ringerMode`，非 `RINGER_MODE_NORMAL` 时弹 Toast 告知用户。

**面试话术**：通知系统我做了三个体验优化——一是紧凑布局，选项用 chip 横排替代列表，信息密度提升；二是预置策略，首次使用就有三个可选策略，降低使用门槛；三是声音试听的边界处理，勿扰模式下原来会崩溃，静音模式下无反馈，分别做了修复。体现的是对用户体验细节的关注。

## 八、云同步系统设计（客户端+服务端）

**问题**：数据只存本地，换设备/卸载后丢失。需要云端同步。

**设计方案**：
```
客户端 CRUD → 标记 syncStatus=PENDING → SyncWorker 上传 → 服务端 upsert
服务端返回 updatedAt > lastSyncTimestamp 的记录 → 客户端 merge
冲突检测：双方都修改 → 生成冲突 → 用户选择 Server/Local 版本
```

**关键决策**：
- 软删除（`deleted=true`）：硬删除后本地无记录，无法同步删除操作到服务端
- `lastSyncTimestamp` 持久化到 DataStore：内存变量进程重启后丢失，导致全量重传
- 增量同步：只传 `syncStatus=PENDING` 的记录，只收 `updatedAt > timestamp` 的记录
- 懒加载 lastSyncTimestamp：不在 init 块里同步读 DataStore，首次 sync() 时用 `.first()` 异步读取

**后端**：Spring Boot + MySQL，9 个 REST 端点，JWT 鉴权。`SyncedTask`/`SyncedCategory` 两个 JPA 实体对齐客户端 DTO。

**踩过的坑**：
1. `runBlocking` + `collect` 读 DataStore 无限 Flow → 主线程永久 ANR。`SyncRepositoryImpl` 的 `init` 块在 Hilt @Singleton 首次解析时执行，`collect` 永不返回导致主线程死锁。修复：删掉 init 块，改用 `.first()` 懒加载。
2. 构造函数/init 块里**绝对不能**用 `runBlocking`，尤其不能 `collect` 无限 Flow。一次性读取用 `.first()`，持续观察用 scope launch。

**面试话术**：同步系统我做了完整的前后端——客户端有 PENDING 标记、增量同步、冲突检测，后端有 upsert、时间戳比较、软删除。踩了一个严重的 ANR 坑：`@Singleton` 的 `SyncRepository` 在 init 块里用 `runBlocking` + `collect` 读 DataStore Flow，但 Flow 是无限流永不结束，导致主线程永久阻塞。这说明对协程生命周期的理解很重要——`collect` 是挂起函数不是阻塞函数，但包在 `runBlocking` 里就变成了主线程阻塞。

## 九、桌面 Widget（Glance）

**实现**：Compose Glance 1.0，显示今日待办前 5 条。

**技术要点**：
- `provideGlance` 是 suspend 函数，可以直接查 Room 数据库，数据通过参数传给 composable
- 不用 Preferences/GlanceStateDefinition：官方推荐的 Preferences 方案在不同版本下兼容性问题多，直查数据库更稳定
- `updatePeriodMillis=1800000`（30 分钟）系统自动刷新 + App 内任务变化时主动调 `updateAll()`
- Widget 点击通过 `actionStartActivity(intent)` 跳转 MainActivity

**踩过的坑**：
1. **Glance 版本**：国内 Aliyun 镜像缓存可能不完整，1.1.0 降级到 1.0.0 才能编译通过
2. **子包导入**：`clickable` 在 `androidx.glance.action`，`actionStartActivity` 在 `androidx.glance.appwidget.action`，Kotlin 通配符导入不递归覆盖子包，必须显式导入
3. **Preferences 方案不可靠**：`currentState<Preferences>()`、`intPreferencesKey` 等在不同版本下有 unresolved 问题，直查数据库绕开了整个 State 机制

**面试话术**：Widget 用了 Compose Glance 1.0。`provideGlance` 是 suspend 函数，我直接在里面查 Room 数据库，绕开了 Glance 的 State/Preferences 机制——这个机制在不同版本下兼容性问题比较多。踩了一个 Glance 依赖版本的坑，国内 Maven 镜像缓存可能不完整，降级到 1.0.0 才解决。另外 Kotlin 的通配符导入不递归覆盖子包，`clickable` 和 `actionStartActivity` 必须显式导入。

## 十、日历月视图

**实现**：手写月历网格（不用第三方库），6×7 布局 + 日期标点 + 下方任务列表。

**技术要点**：
- 月历核心算法：`firstDayOffset = (dayOfWeek - 1) % 7` 计算首日偏移
- `getDatesWithTasksInMonth()` 查询某月有任务的日期集合，用于日历标点
- 日历入口放在 TodayScreen 头部图标，不占用底部导航 Tab

**面试话术**：日历视图我手写了月历网格，没有引入第三方库。核心就是计算首日偏移和月份天数，生成 6×7 的二维数组。数据层新增了按 dueDate 查询的方法和"某月哪些日期有任务"的查询，前者用于显示任务列表，后者用于日历格上的小圆点标记。
