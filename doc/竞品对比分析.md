# NextThing vs 商业待办软件 — 竞品对比与面试话术

> 对标：滴答清单(TickTick)、Todoist、Google Tasks、Microsoft To Do、Things 3
> 目的：明确差距、提炼优势、准备面试深度话术

---

## 一、功能完整度逐项对比

### 1.1 任务核心功能

**NextThing 优势点**：

- 不支持多附件（主流都支持）
- 任务描述不支持 Markdown 格式（Todoist 支持）

### 1.2 智能输入

| 功能 | NextThing | 滴答清单 | Todoist | 面试价值 |
|------|-----------|---------|---------|---------|
| 自然语言解析 | ✅ LLM 解析（DeepSeek/Qwen） | ✅ 规则引擎 | ✅ 规则引擎（业界标杆） | **架构差异大，可深聊** |
| 语音输入 | ✅ 讯飞 ASR（方言支持） | ✅ 系统语音 | ✅ 系统语音 | **有差异化** |
| AI 统计分析 | ✅ LLM 生成周报 | ❌ | ❌ | **独特功能** |

**NextThing 优势点**：
- **LLM 驱动的自然语言解析**：与滴答清单/Todoist 的规则引擎完全不同。用户说"明天下午三点开会，重要"，LLM 解析出日期+时间+优先级+标题，带置信度分数。技术方案更先进。
- **方言语音输入**：讯飞 ASR 支持四川话/粤语等方言，主流 app 用系统语音识别不支持方言
- **AI 统计摘要**：根据任务数据自动生成周报（亮点、问题、建议），主流 app 没有此功能

**差距**：
- LLM 解析速度（网络请求 1-3s）vs 规则引擎（本地毫秒级）
- LLM 解析有幻觉风险，规则引擎确定性高
- 没有 Todoist 的 Ramble 功能（随意说→结构化任务）

**面试深挖方向**：LLM vs 规则引擎的 trade-off。LLM 灵活但慢且有幻觉风险，规则引擎快但覆盖面有限。可以讲"我在项目里选了 LLM 方案是因为个人项目用户量小、灵活度优先，但如果做商业产品会考虑混合方案——先过规则引擎快速匹配，匹配不了再走 LLM"。

## 三、NextThing 独特优势（商业软件没有的）

这些是你面试的杀手锏——每个都能展开讲 2-3 分钟。

### 优势 1：LLM 驱动的智能解析（架构差异）

**别人怎么做**：滴答清单和 Todoist 用规则引擎（正则+日期库），本地毫秒级但覆盖面有限。

**你怎么做**：用户输入自然语言 → 调 DeepSeek/Qwen LLM → 返回结构化 JSON（标题/日期/优先级/分类/置信度）→ 置信度低于阈值时让用户确认。

**面试话术**："自然语言解析我用了 LLM 方案而不是传统的规则引擎。规则引擎的问题是维护成本高——每加一种说法就要写规则，中文的表达方式又特别灵活。LLM 方案通过精心设计的 prompt 可以覆盖各种表达，而且返回置信度分数，低置信度时弹确认弹窗让用户修正。当然也有 trade-off：网络延迟 1-3 秒，有幻觉风险。所以如果做商业产品我会考虑混合方案——先走规则引擎快速匹配，匹配不了再走 LLM 兜底。"

### 优势 2：自定义通知策略系统

**别人怎么做**：滴答清单和 Todoist 都是全局统一通知设置，所有任务用同一套震动/声音/提醒方式。

**你怎么做**：通知策略是独立实体，每个任务可以绑定不同策略。策略包含：震动模式（4级）、声音类型（5种含自定义音频）、音量、系统通知方式（状态栏/横幅/弹窗）、提前提醒时间。预置三条默认策略，用户可自建。

**面试话术**："通知系统我设计成了策略模式——通知策略是独立实体，每个任务绑定一个策略。这样做的好处是用户可以给不同类型的任务配不同的提醒方式，比如工作任务的提醒和健身提醒完全不同。预置了三条策略降低使用门槛。这个设计参考了 Android 的 NotificationChannel 思路，但粒度更细——Channel 是按类别，我是按单个任务。"

### 优势 3：地理围栏 + 双引擎定位

**别人怎么做**：滴答清单有基础地理围栏（到某个地方提醒），单一 Google Play Services 实现。

**你怎么做**：高德 SDK（主力）+ Google FusedLocationProvider（降级）双引擎，Haversine 距离计算，进出围栏判断，延迟通知机制（防止短暂经过频繁触发），月度命中率统计，电池优化感知。

**面试话术**："地理围栏我做了比较完整的方案。定位用双引擎——高德做主力（国内体验好，WiFi+基站 1-2 秒出结果），Google 做降级（海外兼容）。围栏检查不只是简单距离判断，还做了延迟通知机制——用户刚进入围栏时先不通知，等确认停留后才提醒，避免路过就触发的问题。还有月度命中率统计，让用户知道哪些围栏设置是有效的。"

### 优势 4：AI 统计分析

**别人怎么做**：滴答清单和 Todoist 的统计只有图表展示，没有智能分析。

**你怎么做**：将任务统计数据（完成率、分类分布、时间分布、逾期率等）发送给 LLM，生成 100-200 字的中文周报，包含亮点、问题和建议。

**面试话术**："统计模块我加了 AI 分析——不只是展示图表，而是让 LLM 分析用户的任务数据，自动生成周报。比如它会说'本周工作类任务完成率 85%，但运动类只有 30%，建议减少运动任务数量或调整到周末'。这种个性化建议是传统统计图表做不到的。"

### 优势 5：天气联动动态主题

**别人怎么做**：滴答清单/Todoist/Things 3 支持浅色/深色模式切换，但没有动态主题。

**你怎么做**：4 种主题模式（跟随系统/浅色/深色/跟随天气），天气模式预置 9 种天气配色（晴/多云/阴/雨/雪等），每种天气可自定义主色。

**面试话术**："主题系统做了天气联动——选择'跟随天气'模式后，app 的主色调会根据当前天气自动变化。晴天是暖色，雨天是冷色。每种天气的主色用户可以自定义。实现上通过 DataStore 持久化当前天气条件和用户自定义颜色，天气变化时触发 Recomposition。"

### 优势 6：法定假日 + 农历重复规则

**别人怎么做**：滴答清单有法定假日识别，Todoist 没有中文本地化的重复规则。

**你怎么做**：7 种重复频率：每天/工作日/周末/法定假日/自定义周/自定义月。法定假日维护了 2025-2027 年中国法定假日数据（含调休），农历通过 ChineseDateHelper 实现了 2024-2028 年的节气和传统节日。

**面试话术**："重复任务我实现了法定假日和农历支持。法定假日维护了三年的数据包括调休安排，比如国庆放假但周六补班这种。农历方面实现了节气和传统节日计算，可以让任务按'每个农历初一'或'每个立春'重复。这个功能是针对中国用户的，滴答清单有法定假日但没有农历，Todoist 都没有。"

### 优势 7：XLSX 导出手写 OOXML

**别人怎么做**：用 Apache POI 或类似库。

**你怎么做**：手写 OOXML 格式（shared strings table + styled headers + column widths），不依赖 Apache POI，APK 体积不增加。

**面试话术**："数据导出支持 CSV、Markdown 和 Excel 三种格式。Excel 部分没有用 Apache POI，而是手写了 OOXML 格式——包括共享字符串表优化、带样式的表头、自动列宽。这样避免了引入 Apache POI 增加 5MB+ 的包体积。"

## 四、面试整体定位策略

### 不要定位成"又一个 Todo App"

面试时 NextThing 的定位不是"做了一个 Todo App"，而是：

> "NextThing 是一个**AI 原生的个人效率工具**，核心差异化在于三点：LLM 驱动的智能解析、可定制化的通知策略系统、AI 统计分析。技术栈上全面采用现代 Android 技术（Compose + Hilt + KSP + Coroutines + Room），架构上严格遵循 Clean Architecture 三层分离。"

### 和竞品对比的话术模板

如果面试官问"和滴答清单比怎么样"：

> "功能完整度上肯定不如滴答清单，毕竟是个人项目。但有两个方向我认为更有意思：一是 AI 原生设计——自然语言解析和统计周报都用 LLM 而不是规则引擎，这是滴答清单没做的；二是通知系统的灵活度——每个任务可以绑不同的通知策略，比滴答清单的全局设置更精细。当然滴答清单在跨平台、云同步、Widget 这些基础设施上远超我的项目。"

### 面试官可能的追问及应对

| 追问 | 应对 |
|------|------|
| "云同步为什么没做？" | "架构设计完成了——同步状态追踪、冲突解决模型、Retrofit API 都有。后端用 Spring Boot 写了但部署资源有限没上线。如果要做，客户端代码改动很小，主要是后端部署和运维。" |
| "LLM 解析延迟怎么办？" | "目前 1-3 秒可以接受，因为是创建任务时调用不是高频操作。如果要优化，可以做缓存——相似输入命中缓存直接返回。或者混合方案：规则引擎先匹配常见模式，匹配不了再走 LLM。" |
| "为什么用 Compose 不用 View 体系？" | "Compose 是 Android UI 的未来方向，声明式+状态驱动天然适合 MVVM。而且 Compose 的动画系统（成就解锁的粒子爆炸效果）比 View 体系简单得多。" |
| "日历视图为什么没做？" | "在规划中，可以用 Compose Canvas 手写或者集成 Horologist/Calender 库。日历视图的核心是日期-任务的映射查询，Repository 层的 getTasksByDateRange 已经有了。" |
